FDE 職能地圖｜顧問 × 工程的落地轉譯者

FDE 不是「比較會寫程式的顧問」，也不是「比較會簡報的工程師」。真正的定位是：把企業的模糊問題翻譯成可驗證、可交付的技術方案，再把技術限制與結果翻譯回業務價值。

工程世界｜系統、資料、限制、可行性
↔
顧問世界｜問題、流程、價值、利害關係人
工程世界懂到足以判斷可行性、風險與交付方式
系統與架構理解邊界、依賴、非功能需求、技術取捨
資料與整合能力資料流、API、權限、既有系統界接
快速原型與評測用可運行證據驗證，而不是只談概念
Production 約束感知道何時必須交棒給專職工程團隊
FDE 轉譯核心TRANSLATION & DELIVERY CORE
1. Problem Framing｜問題定義把「想要 AI」轉成可解決、可驗證的業務問題
2. Bi-directional Translation｜雙向轉譯Business → Technical；Technical → Business
3. Solution Scoping｜方案切題界定範圍、成功條件、風險與交付順序
4. Rapid Validation｜快速驗證以 PoC、Eval、Prototype 降低不確定性
5. Orchestration｜實作協作與交棒串起顧問、工程與客戶；不是全部自己做
顧問世界懂到足以定義問題、價值與組織採用
商業探索與訪談找出真問題，而不是照單全收需求
流程與問題框架把現象轉成可處理的問題與優先級
價值與決策對齊建立成功條件、取捨與決策共識
採用與變革推進讓方案進入工作流程，而不只完成簡報
FDE 的價值：縮短「建議 → 可行方案 → 驗證 → 落地 → 價值」的距離

角色邊界：FDE 不是什麼

避免「顧問打高空」之後，又把 FDE 推向另一個極端。

✕
不是只做策略簡報的顧問

必須用原型、評測、技術切題與現場採用，證明建議真的能落地。

✕
不是包辦 production 的全能工程師

FDE 要能看懂、能動手驗證，但正式系統的長期品質與維運應有專職 owner。

✕
不是只畫 architecture 的 Solution Architect

FDE 的責任延伸到「方案是否真的解決場域問題」以及採用成效。

✕
不是只做需求管理的 PM

需具備足以挑戰需求與技術方案的工程判斷力，並能快速取得實證。

✓
真正核心：介面層 + 落地責任

把兩種專業語言互相翻譯，持續消除不確定性，直到「可交付、可採用、可量測」。
